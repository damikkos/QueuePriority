# Очередь входа DayZServer и состояние QueuePriority

Разбор сделан 4 ноября 2026 года по QueuePriority v1.1 (`a11e55b`), KR_GRAFTED 0.4.0 и
невыпущенной ветке KR_GRAFTED 0.4.1. Здесь две части: как устроена очередь входа в
DayZ Server 1.29 (это понадобится при переносе на 1.30) и замечания к коду плагина.

## Итог

На DayZ Server 1.29 плагин найдёт всё, что ему нужно: все пять сигнатур однозначны на
трёх сборках, а то, что код предполагает о движке, подтверждается декомпиляцией.

На текущем DayZ Server **1.30.164289 не находится ни одна сигнатура**. Плагин пишет
`unknown DayZServer build` и хуков не ставит, то есть сервер работает как без него.

С KR_GRAFTED 0.4.1 плагин собирается без правок, и секции DLL совпадают побайтно со сборкой
против 0.4.0. ABI 7 и LAYOUT 2 не изменились, так что уже собранная DLL работает и с новым
`hid.dll`.

## Сигнатуры по сборкам

Адреса — VA в файле при базе `0x140000000`. «Сверки» — это проверки из `Install()`: форма
геттера `maxPlayers`, форма счётчика игроков и то, что вызов в Steam-пути ведёт в тот же
геттер.

| Сборка | queue-add | queue-process | player-destroy | steam-update | queue-layout | Сверки |
|---|---|---|---|---|---|---|
| 1.29.0.162510 | `0x14060E130` | `0x14060EB80` | `0x1406C73A0` | `0x140632315` | `0x14060E720` | да |
| 1.29.0.163451 | `0x14060E390` | `0x14060EDE0` | `0x1406C76C0` | `0x140632575` | `0x14060E980` | да |
| 1.29.0.163709 | `0x14060D7A0` | `0x14060E1F0` | `0x1406C6BE0` | `0x140631985` | `0x14060DD90` | да |
| 1.30.164289 | — | — | — | — | — | — |

Каждая сигнатура в сборках 1.29 встречается в исполняемых секциях ровно один раз.

Что известно о 1.30: секция `.text` выросла с 11.3 до 16.5 МБ, то есть сервер собран
заново, а не пропатчен. Фрагмент `44 8B 41 34 33 C0 45 85 C0` из queue-layout не
находится вовсе, `cmp byte [reg+0xAE], 0` встречается дважды (в 1.29 — один раз), а
`44 8B F2 48 8B D9 83 FA 02 75` из player-destroy исчез. Форма геттера `maxPlayers`
(`8B 91 ?? ?? ?? ?? 8B 81 ?? ?? ?? ?? 3B D0 0F 4E C2 C3`) по-прежнему находится один раз.
Значит, переносить придётся и сигнатуры, и, возможно, смещения полей.

## Как устроена очередь в 1.29

Всё ниже снято Hex-Rays со сборки 1.29.0.163451; адреса — её.

### Структуры

| Объект | Смещение | Что там |
|---|---|---|
| очередь | `+0x20` | сервер |
| очередь | `+0x28` | массив игроков (`Player**`) |
| очередь | `+0x30` | ёмкость массива |
| очередь | `+0x34` | число игроков в очереди |
| очередь | `+0x3C` | квота прохода, если больше нуля |
| очередь | `+0x40` | размер, о котором сервер уже знает |
| игрок | `+0x00` | id |
| игрок | `+0x18` | последняя отправленная позиция, при создании `-1` |
| игрок | `+0x24` | имя, 65 байт |
| игрок | `+0xAE` | флаг приоритета |
| сервер | `+0x218` | число игроков — это и есть «онлайн» для очереди |
| сервер | `+0x3C2` | флаг: рассылать игрокам в очереди позиции |
| сервер | `+0x560` | список приоритета: проверяется по SteamID и имени |
| сервер | `+0x77C`, `+0x780` | два лимита; геттер `maxPlayers` отдаёт меньший |
| сервер | `+0x7F2` | флаг: если он стоит, добавление ставит всех в обычную очередь |

Запись игрока занимает `0x140` байт и создаётся в queue-add.

### Добавление — queue-add, `0x14060E390`

Если игрок есть в списке приоритета (и флаг `+0x7F2` не стоит), ему ставится флаг `+0xAE`,
и он вставляется сразу за непрерывным блоком приоритетных игроков в голове очереди. Длину
этого блока считает функция, которую плагин проверяет сигнатурой queue-layout
(`0x14060E980`). Остальные встают в конец. В журнал сервера пишется
`[Login]: Adding prioritized player %s (%d) to login queue at position %d` или
`[Login]: Adding player %s (%d) to login queue at position %u`.

Отсюда следствие для плагина: приоритетные игроки между собой идут по порядку прихода, а
плагин переносит админа на позицию 0. Второй админ поэтому встаёт впереди первого.

### Проход очереди — queue-process, `0x14060EDE0`

```
budget = quota > 0 ? quota − f(очередь) + g() : size   // f и g не разобраны
free   = maxPlayers(server) − online(server) + 1
n      = min(budget, free)
n раз: впустить голову очереди, сообщить ей позицию 0, убрать её из массива
затем разослать позиции оставшимся (0x14060EA50)
```

`online` — это `0x1406BFB40`, то есть `server+0x218`; `maxPlayers` — `0x1406BF4C0`. В теле
прохода `call` на `+0x65` от начала сигнатуры зовёт `online`, `call` на `+0x74` зовёт
`maxPlayers`, возврат из него — `+0x79`. На эти три числа и опирается плагин.

Ветка «админ в голове очереди» в `OnMaxPlayers` возвращает `min(maxPlayers, online)`. Тогда
`free = online − online + 1 = 1`, и проходит ровно один игрок — сам админ. Это держится
только на `+1` в формуле. Если в 1.30 формула станет `maxPlayers − online`, тот же ответ
даст `free = 0`: пока админ стоит первым, не войдёт никто, и очередь встанет. Сейчас `+1`
закреплён самой сигнатурой (`BF 01 00 00 00` — `mov edi, 1`), поэтому при смене формулы
плагин просто выключится. При переносе этот фрагмент из сигнатуры убирать нельзя.

### Рассылка позиций — `0x14060EA50`

Для каждого игрока в очереди, если стоит флаг `+0x3C2`, вызывается проверка
`0x1406396E0`. Если она вернула ноль, игрок передаётся в `0x1406C2650` с кодом и текстом
(по виду — отказ игроку) и убирается из очереди функцией `0x14060EC20` — она пишет
`[Login]: Remove %d from login queue (index %d)`. Иначе, если позиция изменилась
относительно `+0x18`, игроку отправляется новая.

После того как плагин переставил админа в голову, остальные увидят свои новые позиции на
следующем проходе.

### Отключение — player-destroy, `0x1406C76C0`

Пишет `[Disconnect]: Player destroy %d`; для id 2 сразу возвращает `Not implemented.`
Вызывается через обёртку `0x1406C8D00` из `0x1406CC950` и через таблицу виртуальных
функций. Саму очередь входа она не трогает.

Удаление из очереди (`0x14060EC20`) зовут три места: рассылка позиций (выше),
`0x1406BD020` — эта функция сначала убирает игрока из очереди, потом обращается к сетевому
слою (по виду — разрыв соединения сервером), и три ссылки из данных, то есть вызовы через
таблицы виртуальных функций. Их путь не разобран.

**Не установлено**, вызывается ли player-destroy для клиента, который ушёл, ещё стоя в
очереди, и в каком порядке относительно удаления из очереди. Для плагина это важно. Если
игрок исчез из очереди раньше, `OnProcess` посчитает админа вошедшим и добавит в
`g_Online` до вызова destroy. Если destroy для такого клиента не придёт вовсе, запись
останется до перезапуска и будет занимать резерв. Проверить можно на живом сервере: админ
встаёт в очередь и отключается до входа — в журнале сервера должна появиться строка
`[Disconnect]: Player destroy` с его id.

## Замечания к коду v1.1

**1. Нет поддержки 1.30.** Нужны новые сигнатуры и перепроверка смещений `0x28`, `0x34` и
`0xAE`; что именно изменилось — в разделе «Сигнатуры по сборкам».

**2. Админы обгоняют друг друга.** Админ A ждёт, приходит админ B — B становится первым.
Переносить нужно не в 0, а за админов, которые уже стоят в голове:

```cpp
int to = 0;
{
    const std::scoped_lock lock{g_Lock};
    while (to < from && g_Waiting.contains(queue->Players[to]->Id)) {
        ++to;
    }
}
std::rotate(queue->Players + to, queue->Players + from, queue->Players + from + 1);
```

В журнал тогда пишется позиция `to + 1`.

**3. Формула приёма нигде не записана.** В коде нет ни слова о том, что движок пускает
`min(квота, maxPlayers − online + 1)`, почему `min(maxPlayers, online)` даёт ровно
одного игрока и что значат `0x65`, `0x74` и `0x79`. Без этого перенос на 1.30 придётся
начинать с разбора заново. Стоит хотя бы короткого комментария у `OnMaxPlayers` и ссылки на
этот файл.

**4. Детуры без защиты от сбоя.** Исключение или нарушение доступа в `OnAdd`, `OnProcess`
или `OnDestroy` роняет сервер. В KR_GRAFTED 0.4.0 уже есть защищённая форма:
`graft::hooked<&OnAdd>(target, &g_Add)` — сбой пишется в журнал, вызов отменяется.
`OnMaxPlayers` так оборачивать нельзя: внутри обёртки `_ReturnAddress()` укажет на неё, а не
на вызывающего. Об этом тоже стоит оставить комментарий.

**5. Конфиг ищется рядом с exe, а не рядом с DLL.** README обещает «рядом с DLL», но если
положить DLL в `@Mod/grafted` (KR_GRAFTED 0.4.0 это поддерживает), плагин всё равно читает
`DayZServer/grafted/QueuePriority.ini`. Если такой папки нет, файл не создаётся, и резерв со
списком админов выключены. Путь своего модуля даёт
`GetModuleHandleExW(GET_MODULE_HANDLE_EX_FLAG_FROM_ADDRESS, ...)` по адресу любой своей
функции.

**6. Неудачное чтение стирает настройки.** Если в момент входа игрока файл занят
редактором, `Reload()` ставит `Settings{}`: список админов пуст, резерв 0 — до следующего
входа. При ошибке чтения лучше оставить прежние настройки и только написать в журнал.

**7. Тестов в репозитории нет.** Каталог `tests/` в `.gitignore` с коммита `dcb9129`, а
`Parse`, `Public` и `Limit` — как раз та часть, которую легко проверить без игры.

**8. Мелочи.** Вместо `GetModuleHandleW(nullptr)` и `sections_of` есть
`graft::scan::image()`. `Unique()` возвращает `optional` и теряет причину отказа, поэтому в
журнале не отличить «не найдено» от «найдено дважды». У `ReservedSlots` нет верхней
границы: при значении не меньше `maxPlayers` Steam показывает 0 мест, и обычные игроки не
войдут никогда. KR_GRAFTED берётся из соседней папки без версии. Модель потоков не описана:
по разбору всё, кроме Steam-пути, идёт в одном потоке, а Steam-путь читает только
атомарный `g_Reserved`, так что гонки нет — но это стоит одной строки комментария.

## Что сделано хорошо

Адресов в коде нет: всё ищется однозначными сигнатурами и перепроверяется сверками, а на
незнакомой сборке плагин отказывается работать — на 1.30 это подтвердилось. Хуки ставятся
пачкой через `hook_all` в `GRAFT_ON_LOAD`, до запуска потоков движка. Правила вынесены в
`rules.hpp` и не зависят от движка. Определение вызывающего по адресу возврата — способ
поменять поведение геттера только в двух местах, не трогая остальные его вызовы.

## Как проверялось

- **Сигнатуры** — скриптом ниже, который повторяет `Install()` на файле exe.
- **Устройство очереди** — IDA 9.4 и Hex-Rays по базе DayZ Server 1.29.0.163451.
- **Сборка** — clang-cl 20.1.8, с KR_GRAFTED v0.4.0 и с веткой 0.4.1; секции двух DLL
  сравнены побайтно.
- **Вживую плагин не запускался**: очередь не собрать без настоящих клиентов.

```python
# Повторяет Install() из src/plugin.cpp на файле exe: те же сигнатуры, та же проверка
# уникальности по исполняемым секциям, те же производные адреса.
import re
import struct
import sys

SIGS = {
    "queue-add": "4C 89 4C 24 ?? 89 54 24 ?? 55 53 56 57 41 54 41 55 41 56 41 57 48 8D 6C 24 ?? 48 81 EC ?? ?? ?? ?? 4C 8B E9 49 8B F9 B9 40 01 00 00 4D 8B E0 8B DA",

BF 01 00 00 00 48 8B CE 2B F8 E8 ?? ?? ?? ?? 48 8B 74 24 30 03 F8 85 ED 7E ?? 44 3B F7 41 0F 4E FE 0F 1F 44 00 00 85 FF 7E ?? 48 8B 53 28 48 8B CB 48 8B 12 E8 ?? ?? ?? ?? 48 8B 43 28 48 8B 08 8B 11",
    "player-destroy": "40 55 53 41 56 48 8D 6C 24 ?? 48 81 EC ?? ?? ?? ?? 44 8B F2 48 8B D9 83 FA 02 75 ??",
    "steam-update": "49 8B 4D 08 48 8B 18 48 8B 3B E8 [disp32] 8B D0 48 8B CB FF 57 60",
    "queue-layout": "44 8B 41 34 33 C0 45 85 C0 74 ?? 4C 8B 49 28 90 49 8B 14 C1 80 BA AE 00 00 00 00 74 ?? FF C0 41 3B C0 72 ?? 41 8B C0 C3",
}
MAXP = "8B 91 ?? ?? ?? ?? 8B 81 ?? ?? ?? ?? 3B D0 0F 4E C2 C3"
ONLINE = "8B 81 ?? ?? ?? ?? C3"


def compile_sig(text):
    parts = []
    for tok in text.split():
        if tok == "??":
            parts.append(b".")
        elif tok.startswith("["):
            parts.append(b"(....)")
        else:
            parts.append(re.escape(bytes([int(tok, 16)])))
    return re.compile(b"(?=" + b"".join(parts) + b")", re.DOTALL)


def load(path):
    data = open(path, "rb").read()
    pe = struct.unpack_from("<I", data, 0x3C)[0]
    nsec = struct.unpack_from("<H", data, pe + 6)[0]
    opt = struct.unpack_from("<H", data, pe + 20)[0]
    base = struct.unpack_from("<Q", data, pe + 24 + 24)[0]
    secs = []
    for i in range(nsec):
        off = pe + 24 + opt + 40 * i
        vsz, va, rawsz, rawptr = struct.unpack_from("<IIII", data, off + 8)
        ch = struct.unpack_from("<I", data, off + 36)[0]
        secs.append((base + va, data[rawptr:rawptr + min(rawsz, vsz)], bool(ch & 0x20000000)))
    return secs


def read(secs, ea, n):
    for b, raw, _ in secs:
        if b <= ea < b + len(raw):
            return raw[ea - b:ea - b + n]
    return b""


def unique(secs, text):
    rx, hits = compile_sig(text), []
    for b, raw, ex in secs:
        if ex:
            for m in rx.finditer(raw):
                hits.append((b + m.start(), m))
    return hits


def matches(secs, ea, text):
    rx = re.compile(compile_sig(text).pattern[3:-1], re.DOTALL)
    blob = read(secs, ea, len(text.split()))
    return bool(blob) and rx.match(blob) is not None


def call_target(secs, ea):
    return ea + 5 + struct.unpack("<i", read(secs, ea + 1, 4))[0]


def main(path):
    secs = load(path)
    print(path)
    found = {}
    for name, text in SIGS.items():
        hits = unique(secs, text)
        found[name] = hits[0] if len(hits) == 1 else None
        print(f"  {name:15} hits={len(hits)}" + (f" at {hits[0][0]:#x}" if hits else ""))
    proc = found["queue-process"]
    maxp = call_target(secs, proc[0] + 0x74) if proc else 0
    online = call_target(secs, proc[0] + 0x65) if proc else 0
    print(f"  {'max-players':15} {'ok' if maxp and matches(secs, maxp, MAXP) else 'MISS'}")
    print(f"  {'online-players':15} {'ok' if online and matches(secs, online, ONLINE) else 'MISS'}")
    st = found["steam-update"]
    if st:
        disp = struct.unpack("<i", st[1].group(1))[0]
        print(f"  steam call -> {st[0] + 15 + disp:#x}, max-players {maxp:#x}: {'ok' if st[0] + 15 + disp == maxp else 'MISS'}")


for p in sys.argv[1:]:
    main(p)
```
